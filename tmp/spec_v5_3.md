一、设计原则（总纲）
先有尺子，再调参数。 任何改变召回/排序行为的改动（阈值、RRF权重、截断策略、模型版本），必须先有baseline数字，改完必须复测同一批query。禁止凭肉眼顺不顺眼调参。
所有写操作必须幂等。 崩溃重试不能产生重复向量、重复身份、重复日志行。这是resume语义成立的前提。
长任务必须可断可续。 单点超过1小时的流水线，必须支持任意时刻kill后从断点续跑，且不产生脏数据。
两套存储之间必须有reconcile。 SQLite与Qdrant无事务保证，一致性只能靠定期比对修复，不能靠「小心写代码」。
容量必须事前算清，并设水位告警。 沉默失败（NVMe满退化成机械盘随机读）比报错更难排查。
修好的bug必须决定要不要回填。 不回填就要记录空洞范围，并在搜索侧说明。

三、UI全面优化：让每个按钮都有可见结果
3.1 核心问题诊断
「增量扫描/全新扫描没有作用」的感觉，通常源于以下三种情况之一，必须先定位再写代码：

| 可能原因 | 自查方法 | 修复方向 |
|---|---|---|
| A. 任务其实在跑，但UI没反馈 | 点扫描后立即查SQLite tasks表/看进程CPU | 补状态轮询+进度推送 |
| B. 任务跑完但前端没刷新 | 扫描完成后人脸墙数字不变，手动刷新页面才变 | 补完成事件通知+缓存失效 |
| C. 任务真的没生效 | 扫描完成但manifest行数不增 | 查路径过滤规则/glob/扩展名白名单 |

【agent自主决策】 人脸墙不刷新的真实原因由agent按A→B→C顺序实测定位，优先实现B方案（事件驱动+缓存失效）作为默认修复，诊断结果写入日志并可在UI查看。
3.2 任务系统：所有异步操作必须可见
凡是耗时>2秒的操作，一律进入任务队列，并在UI上有对应状态。
任务状态机（统一，所有任务共用）： queued → running → [success | failed | cancelled]，成功/失败都要留历史记录（保留30天）。

| 操作 | 预估耗时 | UI呈现 |
|---|---|---|
| 扫描新文件 | 分钟~小时 | 进度条+已处理文件数+实时速率+预计剩余 |
| 重新扫描全部 | 小时 | 同上+二次确认 |
| 人脸检测与编码 | 小时~天 | 分阶段进度（抽帧→检脸→编码）+可暂停 |
| 人脸聚类 | 2~5h | 阶段进度+「聚类完成后可查看分组」 |
| media路径变更 | 分钟 | 预览差异→确认后执行→校验报告 |
| 库完整性检查 | 分钟~小时 | 后台运行+结果角标 |
| 合并/拆分身份 | 秒 | 立即响应+撤销（5秒内可undo） |

强制交互规范： 1. 任务启动后，按钮变为「进行中」并禁用，不允许重复点击（这是「点了没反应」最常见的成因）。 2. 页面关闭再打开，任务状态必须恢复显示（状态存服务端，不存前端内存）。 3. 失败必须给人话错误信息：不说OperationalError: database is locked，说「有其他任务正在运行，请稍后重试」。 4. 提供「任务历史」面板，可查看每次扫描的时间、处理文件数、新增数、失败数。

四、media路径变更：流程+UI+人脸墙同步
4.1 设计原则（三条铁律）
改路径≠清空库。默认保留所有向量、人脸、身份关系。
原图文件永远由用户管理，系统绝不删除用户文件。
破坏性操作必须「先出报告、后人工确认」。
4.2 变更流程（五步向导，UI上逐步推进）
Step 1 输入新路径 └─ 校验：路径存在/可读/磁盘余量/是否已有媒体文件
Step 2 预览差异（关键步骤，不可跳过） └─ 比对旧路径与新路径，输出：
路径将更新的文件数：N
新路径下新增的文件数：M（需入库）
旧路径下找不到对应文件的数：K（将标为「缺失」）
估计耗时
Step 3 选择保留策略（见下表）
Step 4 执行（进度条+可中断）
Step 5 校验报告+一键触发人脸墙刷新
保留策略（用户可选，默认选①）：

| 策略 | 行为 | 适用 |
|---|---|---|
| ① 保留全部（默认） | 旧数据仍在库、可搜索；缺失文件标missing | 临时换盘、改目录名 |
| ② 隐藏旧数据 | 旧文件标记tombstone，搜索不可见，向量保留 | 确认旧库废弃，想保留身份关系 |
| ③ 彻底清理 | 物理删除向量+Qdrant清理 | 明确要释放空间 |

4.3 路径重映射的实现要点
SQL代码示例：
-- ① 先做dry-run，输出报告，不改数据
SELECT file_path,
       REPLACE(file_path, :old_root, :new_root) AS new_path,
       CASE WHEN file_exists(REPLACE(...)) THEN 'ok' ELSE 'missing' END AS status
FROM files WHERE file_path LIKE :old_root || '\%';

-- ② 确认后批量更新（只改路径，不动face_vectors/semantic_vectors/identities）
UPDATE files SET file_path = REPLACE(file_path, :old_root, :new_root),
                 updated_at = now()
WHERE file_path LIKE :old_root || '\%';

-- ③ Qdrant payload里的file_path由reconcile异步修复，不阻塞主流程
content_hash去重：加content_hash字段后，即使路径全变、只要文件内容没变，就直接复用旧记录，不重新编码。这能把「搬家」的成本从「重跑30小时」降到「几分钟路径更新」。代价是入库时多一次哈希计算。
4.4 人脸墙及时更新的配套动作
路径变更完成后，必须按顺序触发： 1. 失效人脸墙与搜索结果的所有缓存。 2. 触发一次增量reconcile（仅本次涉及的文件），修复Qdrant payload。 3. 向前端广播library_changed事件→人脸墙自动重载。 4. 若采用了策略②/③，额外触发「身份代表项重算」（被删/隐藏的文件可能是某些身份的代表图）。

五、文件增删改配套处理

| 事件 | 系统行为 | 幂等保证 | 人脸墙 |
|---|---|---|---|
| 新增文件 | 入库→抽帧→检脸→编码→向量入库→可选：增量归入现有簇 | uk_face_vector(file_id, shot_ix, face_ix)唯一约束 | 自动出现（事件驱动刷新） |
| 删除文件 | SQLite软删（tombstone+deleted_at）→Qdrant标记→异步GC物理删 | 重复删除不报错 | 自动消失 |
| 移动/改名 | 走第四章路径重映射，不重新编码（需content_hash） | 同新增 | 路径更新，检索不断 |
| 内容被修改 | 旧版本软删+新版本走新增流程；新向量落库成功后才删旧向量 | 同新增 | 自动更新 |
| 外部批量变动（用户手动拷了一万张图进去） | 由「扫描新文件」一次性处理，走批次事务 | 断点续跑 | 扫描完成后整批刷新 |

两条硬约束： - 搜索接口永远以SQLite为准二次过滤Qdrant结果，确保用户永远不会遇到「搜到却打不开（404）」的情况。 - reconcile每日一次全量+每次pipeline完成后一次增量，非零即告警；物理删除必须人工确认。

六、人脸聚类功能
6.1 算法选型

| 人脸数 | 算法 | 理由 |
|---|---|---|
| ≤100万（当前60万在此档） | UMAP降维+HDBSCAN密度聚类 | 簇质量高、原生噪声处理、自动定簇数 |
| >100万或内存吃紧 | Faiss IVF-PQ粗聚类+簇内合并 | 内存可控、速度快，边界簇易碎，需后处理 |

已拍板：采用UMAP降维+HDBSCAN密度聚类。
6.2 参数（先试跑再定，禁止直接全量）
输入：face_vectors表，过滤quality>=门槛的人脸
降维：UMAP(n_neighbors=15, n_components=20, min_dist=0.0, metric=‘cosine’)
聚类：HDBSCAN(min_cluster_size=3, min_samples=2, cluster_selection_epsilon=0.15, metric=‘euclidean’, cluster_selection_method=‘leaf’)
噪声：label==-1→入「未分组」池，后续靠检索兜底
为什么这组起点：n_neighbors=15对人脸这种类内变化大的数据偏保守，不易把同一个人拆碎；min_cluster_size=3避免两人照成簇；epsilon给0.15吸收侧脸/遮挡的漂移。但这些数字必须由M6的金标准集验证，不许凭感觉定死。
6.3 规模与预算（按N=60万，维度d以实际模型输出为准）

| 项 | 估算公式 | 值 |
|---|---|---|
| 原始向量 | N×d×4B | d=512→≈1.2GB；d=128→≈0.3GB |
| UMAP嵌入 | N×20×4B | ≈48MB（可忽略） |
| UMAP峰值内存 | 邻接图+优化缓冲 | 预留16~32GB |
| HDBSCAN | condensed tree | 2~6GB |
| 聚类总耗时 | — | 2~5h（SSD不瓶颈时） |
| Qdrant索引 | — | 2.5~3.5GB（含payload） |

硬约束： 1. 必须先跑10万样本试跑，记录内存峰值与耗时，线性外推至60万；外推超内存则降级为「分块聚类+质心合并」（不做IVF-PQ，保持算法单一）。 2. 聚类产物带版本号落盘：clusters/v{yyyyMMdd_HHmm}/assignments.parquet + centroid.npy + config.json，支持一键回退。 3. 切换原子化：新簇写新快照→校验通过率→原子切换current_cluster_version，搜索服务不中断。
【agent自主决策】 关于「60万」口径：agent按「检测到的脸」（含未过质量门的人脸）进行容量预算和方案设计。在M7执行10万试跑时，必须同时统计实际检测到的脸总数和过质量门后的人脸数，若两者差异超过2倍，暂停全量聚类并汇报用户。
6.4 质量评估（不可绕过）

| 项目 | 规格 |
|---|---|
| 人脸金标准集 | 1,000~2,000张人脸，人工标注簇内同否+随机跨簇对 |

7.1 缓存策略B：命中缓存+LRU（落地细节）
核心思想：不预生成，只在「被检索命中/被人脸墙展示」时生成缩略或抽帧缓存，空间自限。
缓存目录结构：
<cache_root>/
  thumb/   <content_hash[:2]>/<content_hash>.webp   # 人脸墙缩略
  frame/   <content_hash[:2]>/<content_hash>_<shot_ix>.jpg  # 抽帧关键帧
  meta.db  # LRU记账：key, size_bytes, last_hit_at
缓存规则表：

| 规则 | 设定 |
|---|---|
| 缓存键 | content_hash（不是路径！路径会变，hash不变） |
| 上限 | NVMe余量的60%，且绝对不超过50GB（可配置） |
| 淘汰 | LRU，低峰后台批删，每次≤2000个文件，删完更新meta.db |
| 缺失回源 | 缓存未命中→回原图/原视频读取→写缓存→返回（首次慢，之后快） |
| 告警 | 使用率>80%告警，>90%暂停写入并临时关闭缓存生成 |
| 一致性 | 文件被删/改→按content_hash同步清对应缓存项 |

优点：搬家、改路径、换盘都不影响缓存命中率；同一张图出现在两个文件夹也只存一份。
7.2 content_hash落地
DDL：
ALTER TABLE files ADD COLUMN content_hash CHAR(64);
CREATE INDEX idx_files_hash ON files(content_hash);
ALTER TABLE files ADD CONSTRAINT uk_path UNIQUE(file_path);  -- 路径仍唯一
关键：去重语义落在hash上，而非路径
INSERT INTO files(file_path, content_hash, ...)
VALUES (:path, :hash, ...)
ON CONFLICT(file_path) DO UPDATE SET content_hash=excluded.content_hash, updated_at=now();
入库流程变更： 1. 新文件→算content_hash（小文件全量MD5；视频取首段固定字节+时长+分辨率做复合指纹，避免大文件哈希耗时） 2. SELECT file_id FROM files WHERE content_hash=:hash AND deleted_at IS NULL - 命中→复用旧file_id，只增/更路径，跳过抽帧、检脸、编码（向量、人脸、身份关系全部保留） - 未命中→走正常F链 3. 移动/改名→hash命中→仅UPDATE file_path，零重算
代价：每次入库多一次哈希（图片毫秒级，视频取指纹更快）。收益：搬家从「重跑30小时」降到「几分钟路径更新+少量新增」。
视频指纹方案（已拍板）：采用「首帧哈希+文件大小+时长」三元组。误差率可接受。
7.3 media路径变更（策略①保留全部，已拍板）
五步向导不变，第三步默认选中「保留全部」并灰掉其他两项（高级用户可在「维护」页手动改）。
关键点：策略①下，旧路径数据一条不删，只打标记。
SQL示例：
-- Step 2 预览差异（dry-run，只读）
WITH mapped AS (
  SELECT file_id, file_path,
         REPLACE(file_path, :old_root, :new_root) AS new_path
  FROM files WHERE file_path LIKE :old_root || '%' AND deleted_at IS NULL
)
SELECT COUNT(*) AS will_update,
       SUM(CASE WHEN file_exists(new_path) THEN 1 ELSE 0 END) AS ok,
       SUM(CASE WHEN NOT file_exists(new_path) THEN 1 ELSE 0 END) AS missing
FROM mapped;
7.4 Baseline与自动阈值标定（已拍板）
7.4.1 用户要做什么（UI上给用户的说明文案）
金标准集是什么 请你准备一个文件夹，里面按「人名」建子文件夹，每个子文件夹放这个人的若干张照片（每人5~20张即可，正脸、侧脸、戴眼镜、遮挡各放几张更好）。 系统会读取这些照片，两两计算相似度，自动画出一条「准确率—召回率」曲线，并帮你选出最合适的识别灵敏度。 你不需要手写任何表格，也不需要填数字。 注意：这些照片只用于计算阈值，不会被加入你的素材库，也不会被上传。
目录约定：
<gold_root>/
  张三/ 001.jpg 002.jpg ...
  李四/ 001.jpg ...
  _negative/  # 可选：放明显不是库内任何人的照片，用于估false positive
规则：子文件夹名=身份；同一文件夹内=同人；跨文件夹=不同人；_开头的文件夹忽略。
金标准集照片来源（已拍板）：可以用库里已有的素材截图或者是外部照片，由系统判断。用户可以指定路径，一个路径下是一个人。
7.4.2 系统做什么（全自动，无人工介入）
扫描gold_root，构建真值对集合：
同人对=所有intra-folder组合（上限每身份采样C(20,2)=190对，防爆炸）
异人对=跨文件夹随机采样，数量=同对人×2（保证负样本充足）
批量算相似度：复用已有编码管线，走batch，GPU/CPU均可。
阈值扫描：在[0.20, 0.70]以步长0.02扫描阈值，逐档计算recall@20/precision@20。
选点策略：recall@20≥0.95约束下取precision最高；无满足点则取recall最高点的下一档。
产出文件：
gold/result_{timestamp}.json ← {chosen_threshold, curve: […], per_identity: {…}}
gold/pr_curve.png ← 曲线图
gold/false_positives.csv ← 该阈值下被判为同人的错误对（人工复核用，最能发现标注错误）
写回config：threshold=chosen_threshold，并记录old→new到审计日志。
UI提示：「建议灵敏度由0.55调整为0.38（召回95%，精度66%），是否应用？」+一键应用/拒绝。
样本量不足降级策略（已拍板）：若用户只给了1~2个人、每人2张，样本量不足时，报错提示「至少3个身份、每身份≥5张」，并给出一个默认阈值（0.40）作为降级方案，用户可选择应用默认值或重新提供数据。
重要约束：阈值改动后，必须自动重跑那200条query baseline，产出diff表，确认整体没退化才允许合并。
7.5 孤儿向量：只做检测报告（已拍板）
reconcile输出reconcile_report_.json： - A. 孤儿向量（Qdrant有，SQLite已删/tombstone）—— count + 样例20条 - B. 悬空引用（SQLite有向量ID，Qdrant查不到） - C. payload漂移（file_path/tombstone不一致）
动作： 报告用户，由用户确定是否删除

八、一致性与恢复性设计（P0）
8.1 双写一致性协议
SQLite（元数据）与Qdrant（向量）之间无事务，采用「SQLite为权威源+软删优先+定期reconcile」模型：

| 操作 | 顺序 | 失败处理 |
|---|---|---|
| 新增 | ①写SQLite（含向量ID占位）②upsert Qdrant（带file_id payload）③回写Qdrant向量ID到SQLite | ②失败→整批rollback，记dead_letter，不产生孤儿向量 |
| 删除 | ①SQLite软删（tombstone+deleted_at）②标记Qdrant payload tombstone=true ③异步GC物理删 | ②失败不影响搜索结果（search已过滤tombstone）；GC可无限重试 |
| 修改 | 等价于「删旧版本+新增」，旧向量保留至新向量落库成功后再删 | 见幂等键 |
| 搜索降级 | Qdrant返回的ID必须在SQLite能查到且非tombstone，否则静默丢弃并计数告警 | 用户看到的结果数偏少，绝不会出现404 |

关键约束：搜索接口永远以SQLite为准做二次过滤。这使「Qdrant多、SQLite少」的不一致对用户不可见，只剩「SQLite多、Qdrant少」一种可见形态（表现为漏召回），后者靠reconcile修复。
8.2 Reconcile任务
频率：每日一次全量（离线低峰）+每次pipeline完成后一次增量（仅本批次file_id）。
产物：reconcile_report_.json，含三类异常计数与样例，非零即告警。
自动化边界：脚本只做检测与生成修复计划，物理删除必须人工确认（避免误删不可逆）。
8.3 幂等键与断点续跑
DDL：
CREATE UNIQUE INDEX uk_face_vector ON face_vectors(file_id, shot_ix, face_ix);
CREATE UNIQUE INDEX uk_semantic ON semantic_vectors(file_id, shot_ix);
-- 所有插入一律 INSERT OR IGNORE / ON CONFLICT DO NOTHING
manifest三态扩展为五态：pending/running/done/failed/skipped_dup，running态带lease超时（进程死掉后自动回pending，避免永久卡死）。
编码阶段checkpoint：每N个文件flush一次offset到pipeline_state表，重启从最后一个完整checkpoint续跑。
CLI约定：–resume默认开启；–force-rebuild 用于单文件重跑；–from-stage L2c用于跳过已完成层级。
必须实测一次「跑到一半kill -9再resume」的演练，并记录：续跑耗时、行数单调性、有无重复向量。这项不通过，30小时的ETA没有意义。

十、历史数据回填（P1）
已修复的两个bug（代表项淘汰不换人、quality标定错挡人脸）与一次补行（fix-skipped-dup补11,973行）只对增量生效，存量存在永久空洞。

| 对象 | 影响范围 | 处理方式 |
|---|---|---|
| 代表项淘汰没换人 | 去重阶段被淘汰且无替补的代表文件 | 无法恢复（原图若仍在磁盘，走「缺失代表项重扫」路径；若已不在，永久丢失）→产出backfill/lost_representatives.csv记录空洞范围 |
| quality错挡人脸 | 被误判为低质量的2/3人脸 | 重跑F链（复用已抽帧缓存，成本可控）→backfill –stage F –affected |
| skipped_dup补行期间 | 那段时间入库的文件 | 已补行，需做一次reconcile-C类检查确认无悬空引用 |

回填策略（已拍板）： - 代表项丢失：大概率无法恢复，agent产出空洞范围报告（backfill/lost_representatives.csv），书面接受损失。 - quality错挡：建议回补，成本可控（复用已抽帧缓存），agent执行回补并产出报告。 - skipped_dup补行期间：已补行，agent做一次reconcile-C类检查确认无悬空引用。
原则：回填必须支持dry-run、分批（每批≤5,000文件）、可中断续跑，且不得改变已成功文件的向量ID（否则搜索侧会出现旧ID失效）。

十一、测量口径修正（P1）
p99改为p99.9。 当前最大值640ms而p99仅13ms，尾部比p99厚50倍——p99已经把尾巴抹平了，用它做SLO会系统性低估风险。
5%的锁代价是照片阶段的下界，禁止写进总ETA。 视频阶段一个事务写几十个shot，锁持有时间非线性增长；且抽帧与编码的相对速度变化会改变争抢频率。视频链必须独立重测这套探针。
阳性对照补充动态竞争场景。 现有注入4s静态锁只证了探针灵敏度，未证明「两个writer真实轮流抢锁」能被准确量化。补一个并发压测：双writer持续写入10分钟，统计等待分布与err字节数。
ETA必须带置信区间。 照片链写成「29~30h（基于当前并发与无错误假设）」，视频链写成「未知，待100样本试跑」。

十五、Agent自主决策事项（本版本新增，替代此前的「仍待确认」章）
本章列出所有此前标记为「待确认」的事项，现已给出默认决策并授权agent在合理技术范围内自主判断实现细节。agent执行时遇到以下事项无需暂停汇报，按本文默认决策执行即可；仅在偏离默认决策超过合理范围时才需汇报。
15.1 「60万」口径问题
背景：之前一直说「60万张人脸」，但从未明确这是「检测到的脸」还是「过质量门后的人脸」，两者能差3倍，直接决定聚类要不要换算法。
默认决策：按「检测到的脸」（含未过质量门的原始检测结果）进行容量预算和方案设计。UMAP+HDBSCAN的预算表按此口径编制。
agent执行要求： - 在M7执行10万样本试跑时，必须同时统计两个数字：(a) 检测到的脸总数 (b) 过质量门后的人脸数。 - 若(b)/(a) < 0.5 或 (b)/(a) > 0.9，说明质量门设置可能有问题，需调整quality阈值后重新统计。 - 若实际过质量门后的人脸数超过100万，触发降级方案：分块聚类+质心合并（不做IVF-PQ，保持算法单一）。 - 统计结果写入baseline报告，供后续容量规划参考。
15.2 配置文件与表名处理
背景：之前要求用户提供配置文件完整内容和真实表名/字段名，否则阻塞M2/M4/M8的DDL编写。
默认决策：授权agent在系统启动时自动发现schema，不硬编码表名。配置驱动而非文件驱动。
agent执行要求： - 启动时探测SQLite数据库，自动列出所有表名、字段名、索引信息。 - 探测Qdrant collection列表及payload结构。 - 将发现的schema信息展示在「关于/系统状态」页，供用户确认或修正。 - 提供配置文件（如config.yaml）仅用于覆盖默认值（如连接字符串、路径、阈值等），核心表名/字段名从数据库元数据读取。 - 若探测失败（表不存在），给出清晰的错误提示和修复建议，而非静默崩溃。 - 写入启动日志：「已发现N个表：xxx；已发现M个collection：xxx」。
15.3 人脸墙不刷新问题
背景：用户反馈「增量扫描/全新扫描没有作用」，原因可能是A（UI没反馈）、B（前端没刷新）、C（任务没生效），此前一直未定位。
默认决策：授权agent按A→B→C顺序诊断并修复，默认实现B方案（任务完成事件+局部刷新）作为通用修复。
agent执行要求： - 诊断阶段：在任务执行日志中增加诊断输出，依次检查：(A) 扫描时tasks表是否有记录、进程是否有CPU占用；(B) 扫描完成后前端是否收到事件通知；(C) manifest行数是否实际增加。诊断结果写入日志文件。 - 修复阶段：默认实现B方案——任务结束时写task_events表，前端通过SSE或长轮询订阅事件，收到事件后刷新受影响区域。 - 兜底：若B方案改造量过大，先实现A方案（前端定时轮询统计接口）作为临时兜底，确保用户能看到进度。 - 验收：扫描/聚类/增删改完成后，人脸墙在3秒内自动刷新，无需手动刷新页面。
15.4 历史数据回填策略
背景：已修的两个真 bug（代表项淘汰不换人、quality标定错挡人脸）和一次补行（fix-skipped-dup补11,973行）只对增量生效，存量存在永久空洞。
默认决策： - 代表项丢失：大概率无法恢复（原图可能已不在磁盘），agent产出空洞范围报告（backfill/lost_representatives.csv），书面接受损失。 - quality错挡：建议回补，成本可控（复用已抽帧缓存），agent执行回补并产出报告。 - skipped_dup补行期间：已补行，agent做一次reconcile-C类检查确认无悬空引用。
agent执行要求： - 回填脚本必须支持dry-run模式（只输出计划，不执行修改）。 - 分批执行，每批≤5,000文件，支持中断续跑。 - 不得改变已成功文件的向量ID（否则搜索侧会出现旧ID失效）。 - 产出backfill_report_.json，含：处理文件数、成功数、失败数、空洞范围。 - 物理删除操作必须经「维护页→勾选报告→确认」，禁止自动执行。
15.5 日志与监控对接方式
背景：之前要求明确「err日志非零即告警，往哪发」，但用户未指定具体对接方式。
默认决策：默认实现本地轮转日志+UI角标告警，同时预留webhook接口供后续对接外部系统。
agent执行要求： - 日志：使用轮转文件日志（如logrotate策略，单文件最大100MB，保留最近10个文件），日志级别可配置（DEBUG/INFO/WARNING/ERROR）。 - 告警：err日志非零时，在UI右上角显示红色角标计数；访问维护页时展示最近错误摘要。 - webhook接口：预留一个可配置的webhook URL（在L2高级设置中），当严重错误发生时HTTP POST发送JSON通知。默认关闭，用户配置后生效。 - 结构化日志：关键事件（任务开始/完成/失败、配置变更、reconcile结果）输出结构化JSON行，便于后续接入ELK等日志平台。 - 性能指标：暴露一个/metrics接口（Prometheus格式），输出QPS、延迟p50/p95/p99、错误率等指标。
15.6 聚类上线窗口与回滚方案
背景：聚类上线需要保证搜索服务不中断，且出问题能快速回滚。此前未明确上线窗口和回滚策略。
默认决策：授权agent设计版本指针原子切换方案，实现零停机上线和秒级回滚。
agent执行要求： - 版本管理：每次聚类产出带版本号（v{yyyyMMdd_HHmm}），产物落盘到clusters/v{version}/目录，包含assignments.parquet、centroid.npy、config.json。 - 原子切换：维护一个current_cluster_version指针（存SQLite配置表），切换时仅更新指针值（单行UPDATE，原子操作），搜索服务读取指针获取当前版本路径。 - 上线流程：新聚类完成→自动跑质量校验（recall/precision对比baseline）→通过后更新指针→搜索服务下一请求自动生效。 - 回滚方案：若上线后发现问题，一键回滚到上一版本指针（配置表UPDATE），搜索服务下一请求自动切换到旧版本。回滚操作写审计日志。 - 上线窗口：无需停机窗口，切换在秒级完成。但建议在低峰期执行首次全量聚类，降低风险。 - 保留策略：保留最近3个版本的聚类产物，超过3个的自动清理（最旧的一个），释放磁盘空间。
15.7 双胞胎/多人同脸场景
背景：用户场景中可能存在双胞胎或长得极像的陌生人，这些case会导致聚类误判（不同人分到同一簇）和检索误报（搜A出来B的照片）。
默认决策：授权agent在金标准评估中增加「同脸不同人」误报率指标，并在聚类质量报告中单独列出。
agent执行要求： - 在金标准集构建阶段，若用户能提供已知的双胞胎/高度相似人脸case，agent应将其纳入测试集。 - 评估指标增加：「同脸不同人误报率」= 被错误分配到同一簇的不同人对数 / 总不同人对数。 - 聚类结果中，对每个簇输出置信度评分（基于簇内样本间平均相似度），低置信度簇（平均相似度<0.45）标记为「待审核」。 - UI提供「低置信度簇待审核队列」，管理员可逐簇查看并手动修正。 - 若用户场景中没有已知的双胞胎case，agent应在报告中注明「未检测到同脸不同人风险，建议后续补充测试」。

-- ③ 单调性快照（记下来，明天同一时间再跑一次，必须不减）
SELECT max(updated_at), count(*) FROM semantic_vectors;

df -h <nvme_mount> && du -sh <cache_dir>
