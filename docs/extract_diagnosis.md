# 03_extract 实跑诊断报告

> 起因：你贴的 `03_extract.py` 输出里大量看似"抽帧失败"的 WARNING。
> 结论：**这些警告绝大多数不是故障**，但**真实瓶颈在别处，而且很严重**。

---

## 一、先给结论

| 你看到的 | 性质 | 影响 |
|---|---|---|
| `mjpeg: Non full-range YUV ...` + `Error while opening encoder` | **次生现象**。真正原因是 seek 越过了视频最后一帧 → 没有帧到达编码器。mjpeg 的报错只是编码器"空转初始化"时抛出的噪声 | 只影响**每个镜头的最后一帧**，该镜头仍有其他帧 |
| `全黑/近黑（均值 x <= 5.0）` | **按设计工作**。这些确实是暗场/纯色帧 | 丢弃是正确的；但对夜景/黑底素材偏严 |
| `体积过小 17xx B <= 2048B` | **按设计工作**。1769 B 的 682×384 JPEG 就是接近纯色的帧 | 同上 |
| `h264: Invalid NAL unit size` | **源文件损坏**，不是代码问题 | 该文件标记 error，符合"单文件失败不中断整批" |
| `镜头密度异常` | **按设计工作**（规格 L2b 要求告警） | 无 |

实测数据（`shots` 表）：

```
shots 总数   : 2,131
关键帧总数   : 4,102
0 帧的镜头   : 2   (0.1%)
```

**镜头的关键帧丢失率 0.1%** —— 这些警告没有损坏索引。

## 二、mjpeg 报错的完整证据链

### 1. 精确复现

取日志里 14 个真实失败点，在**正确的文件 + 正确的 ts** 上重跑：

```
日志 ts 处失败：14/14
改用「实际末帧 -0.1s」成功：14/14
```

### 2. 关键观察

```
file_id  容器时长   日志ts     ts原值   ts-0.5   ts-1.0   末帧-0.1
      1    587.30   587.25     FAIL     FAIL     FAIL       OK
      3   1312.88  1312.83     FAIL       OK       OK       OK
      4   3003.08  3003.03     FAIL       OK       OK       OK
     55     19.32    19.27     FAIL       OK       OK       OK
```

`日志 ts` 与 `容器时长` **几乎相等**（差 0.05s）——这正是代码里
`frame_timestamps()` 的 `shot.end - eps` 分支。

### 3. ffmpeg 完整输出

```
[vf#0:0] No filtered frames for output stream, trying to initialize anyway.   ← 真因
[mjpeg]   Non full-range YUV is non-standard, set strict_std_compliance ...    ← 次生
[mjpeg]   ff_frame_thread_encoder_init failed
[vost]    Error while opening encoder - maybe incorrect parameters ...
[out#0]   Nothing was written into output file
```

第一行才是根因：**没有帧到达编码器**。

### 4. margin 实测（15 个真实视频）

```
fid    时长      ts=时长   时长-1   时长-3   时长-5
  1   587.30      FAIL     FAIL     FAIL      OK     ← 容器时长比实际末帧高 4.5s
  2  2631.61      FAIL       OK       OK      OK
  3  1312.88      FAIL       OK       OK      OK
 ...（其余 12 个同样）
```

- `ts = 容器时长` → **15/15 失败**
- `时长 - 1` → 14/15 成功（fid=1 因尾部空洞大仍失败）
- `时长 - 5` → **15/15 成功**

**修复**：把抽帧时间点钳制到 `duration - margin`（建议 5s），
或对失败点做「回退重试」（`ts -= 0.5, 1.0, 2.0, 5.0`）。
这是 3 行改动，能消除全部 mjpeg 警告。

## 三、真正的瓶颈：视频解码，不是抽帧

76 分钟实测：**已完成 1,500 / 435,082**，关键帧 12,971 → 13,689。

```
平均产出 3.0 关键帧/秒
目录增长 1~2 个/分钟（每个目录 = 一个视频）
```

推算：

| 阶段 | 数量 | 单价 | 小计 |
|---|---|---|---|
| 视频 | 22,149 | ≈ 30 s | **≈ 185 小时** |
| 照片 | 412,933 | ≈ 20 ms | ≈ 2.3 小时 |

**按当前实现，全量抽帧约需 185 小时（7.7 天）**，且几乎全耗在视频上。

### 为什么这么慢

每个视频被**完整解码两次**：

1. **PySceneDetect** `detect_scenes()` —— 全片逐帧解码做内容差分（主要成本，CPU 单线程）
2. **ffmpeg 抽帧** —— 每次 `-ss` 都要再解码

而 `video.hwaccel: auto` 实际未启用硬件解码（代码里只有 `hwaccel == "cuda"` 时才加
`-hwaccel cuda`，而配置值是 `auto`）。

## 四、可选的处理方向

| 方案 | 改动量 | 预计效果 | 风险 |
|---|---|---|---|
| **A. 接受 185 小时** | 0 | 一周多跑完 | 期间无法验证检索效果 |
| **B. 只修 mjpeg（时间钳制）** | ~3 行 | 消除全部 mjpeg 警告；不影响耗时 | 无 |
| **C. B + 启用硬件解码** | ~5 行 | 取决于驱动，视频解码可能快 2~5 倍 | 需回退逻辑（已具备） |
| **D. C + 用 ffmpeg 单遍同时做镜头切分** | 中等 | 省掉一次完整解码，可能 2~3 倍 | 需要改切分实现，行为会和 PySceneDetect 有差异 |
| **E. 先跳过长视频，优先跑完 41 万照片** | 小 | 几小时内先拿到可用的图片检索库 | 视频暂时不入库 |
| **F. 降低采样：`max_frames_per_shot` 3、长镜头采样 0.5/s** | 配置 | 关键帧少一半，解码量不变（解码才是瓶颈） | 精度略降 |

**我的建议**：先做 **B（3 行，消除误导性警告）**，再决定 C/D。
若你希望尽快看到检索效果，**E** 是最快的路径——41 万照片 2.3 小时就能全部入库并可用。
